## 1. 版本目标与范围

本版定位为“可选的消息容量治理与页面生命周期扩展”。优先解决提示堆积、过期消息继续显示，以及单 Activity 应用中消息不能随 Fragment 页面结束的问题。

| 优先级 | 本版交付 | 用户价值 |
| --- | --- | --- |
| P0 | 显式开启的待处理容量、等待有效期和去重历史容量 | 限制高频调用造成的积压，让失去时效的提示及时结束 |
| P0 | 独立的 `ktoast-lifecycle` 扩展模块 | 绑定 `LifecycleOwner`，支持 Fragment View 生命周期，不增加核心依赖 |
| P0 | 1.1.0 API 基线、旧消费者与新增边界回归 | 保护已发布接口和默认行为，避免扩展功能破坏旧业务 |
| P0 | 入口选择说明、迁移示例和 Demo | 让使用者知道全局、Activity 和 LifecycleOwner 入口的适用边界 |

本版不包含 Compose 专用模块、多窗口同时独立展示、操作按钮体系、优先级调度、全局 Flow 事件总线，以及后台送达保证。Compose 专用适配建议作为后续独立版本，避免同时引入生命周期、UI 状态和发布工具三类变化。

本版也不顺带升级 AGP、Gradle、Kotlin 或核心生产依赖。AGP 8.6 与 compileSdk 36 的官方支持范围风险继续如实记录，工具链调整另行评估。

## 2. 已确认基础与兼容要求

当前已经具备请求句柄、串行调度、分组取消、四种展示模式、Activity 作用域、主线程窗口操作及回调异常隔离。实现应沿用这些能力，不重写调度器或窗口策略。

相关入口：

- [KToast](../../library-android/src/main/java/com/logan/ktoast/KToast.kt)：待提交、延时任务、全局与页面请求入口。
- [ToastDispatcher](../../library-android/src/main/java/com/logan/ktoast/runtime/ToastDispatcher.kt)：展示、排队、防抖、去重、取消和终态回调。
- [KToastScope](../../library-android/src/main/java/com/logan/ktoast/KToastScope.kt)：Activity 状态与取消代次。
- [页面作用域说明](../PAGE_SCOPE.md)：已发布行为约定。
- [1.2.0 验收记录](../releases/1.2.0.md)：实际验证证据及尚未覆盖项。
- [发布指南](../RELEASING.md)：当前双模块发布步骤。

实施必须满足以下约束：

1. 核心保持 minSdk 21、JVM 1.8、Kotlin metadata 1.9，以及 stdlib 1.9.23、Startup 1.1.1 生产依赖。
2. 不修改已发布 `KToastConfig`、`KToastBehavior`、`KToastCallbacks`、`KToastScopeOptions` 的主构造参数，不改变其既有 `copy`、`componentN` 和默认参数方法签名。
3. 不向既有状态、结束原因、展示模式和诊断事件枚举增加成员。新增信息通过新类型及可选属性表达。
4. 未开启运行策略时，旧全局与 Activity 入口保持 1.1.0 行为，包括无默认容量上限、全局替换/取消含义、旧延时返回 `Runnable` 及回调语义。
5. 现有 Activity 作用域继续在停止时取消、恢复后可复用；新生命周期扩展的内部代理更换不改变这个旧接口。
6. `onShow`/SHOWN 和系统完成计时仍不保证实际送达，不借本版修改这些兼容语义。

## 3. 可选运行策略

### 3.1 公开入口

建议新增不可变的 `KToastRuntimePolicy`，通过 `KToast.setRuntimePolicy(policy)` 配置。样式继续由 `KToast.config` 管理，运行策略不加入旧样式或行为配置构造。

以下是拟新增 API 的使用示例，当前 1.1.0 尚不能编译：

```kotlin
// 放在 Application 初始化阶段，并早于任何提示请求或延时任务。
KToast.setRuntimePolicy(
    KToastRuntimePolicy(
        maxPendingRequests = 32,
        maxQueueWaitMillis = 10_000L,
        maxDedupeEntries = 256
    )
)
```

| 参数 | 默认值 | 开启后的含义 |
| --- | --- | --- |
| `maxPendingRequests` | `null` | 全库尚未开始展示的有效请求/延时任务总数上限 |
| `maxQueueWaitMillis` | `null` | 请求具备展示资格后允许等待的最长时间 |
| `maxDedupeEntries` | `null` | 全库去重历史条目上限 |

`null` 表示保持旧规则；启用值必须大于零。示例数字只用于演示，不作为已测得的最佳生产配置。

配置须在主线程、初始化完成后、首个有效请求或旧延时任务登记前执行。在首次登记时原子冻结配置，之后尝试修改应明确抛出 `IllegalStateException`，避免已有队列被动态配置隐性改变。首次登记前可重新配置；参数校验失败不得冻结配置。调试入口被关闭或扩展入口因空内容直接返回时，不视为有效登记。

冻结与容量预留必须共用可验证的同步边界，防止工作线程提交和主线程配置交错。冻结的是配置快照，不是全局样式对象。

### 3.2 容量统计与溢出规则

`maxPendingRequests` 作用于旧全局入口、Activity 作用域和生命周期扩展，统计范围包括：

- 已登记但仍在准备配置或等待主线程处理的请求。
- 已进入队列或防抖槽位的请求。
- 尚未触发的页面延时请求和旧 `Runnable` 延时任务。

正在展示的请求不占待处理额度。同一请求跨阶段迁移只占一个额度，旧延时任务触发时转移额度，不先归还再重新申请。

本版只实现一种溢出规则：**保留已接受请求，拒绝新请求**。不增加淘汰策略枚举、优先级或按组配额。达到上限时返回的句柄仍需进入唯一终态；旧无返回值入口直接结束该请求；旧延时入口仍返回可安全撤回的 `Runnable`，拒绝后不会显示。

准入发生在局部配置 DSL 执行前，避免已拒绝请求继续构造配置或 View。额度预留、释放需幂等；DSL 抛错时释放额度并保留原有异常传播方式，不把编程异常吞成普通取消。

启用上限意味着 `REPLACE` 在待处理额度耗尽时也可能被拒绝，并且不会提前取消现有提示。这是显式限流的行为取舍，必须在文档和测试中说明，不能宣传为开启限流后所有模式仍无条件接受新消息。去重检查也发生在准入之后，过载时新重复消息可能以容量拒绝结束。

容量约束针对库登记的有效待处理项，不代表整个进程的内存硬上限。调用方持有的对象、正在执行的业务 DSL，以及等待主线程发送的终态回调仍有各自成本。主线程被长时间阻塞时，任何方案都不能保证回调及时执行。

### 3.3 等待有效期

使用单调时钟 `SystemClock.uptimeMillis()`，不使用系统日期计算截止时间。所有时间加法进行溢出保护。

定义 `eligibleAt` 为请求最早具备展示资格的时间：普通请求从调用时起算，延时请求从计划触发时间起算，防抖请求从本轮防抖窗口结束时间起算。延时与防抖串联时，按实际进入防抖阶段的起点确定窗口，不把两个阶段混为同一次延时。

`expiresAt = eligibleAt + maxQueueWaitMillis`。例如，延时 30 秒、允许等待 10 秒的请求，不应在调用后第 10 秒过期；计划触发后等待超过 10 秒才过期。旧延时任务也需保留计划触发时间，不能在迟到执行时重新起算以掩盖主线程积压。

在配置准备结束、主线程接纳、延时/防抖触发和实际展示前复核资格、取消代次及截止时间。已过期的 `REPLACE` 不得取消现有有效提示；已过期请求不得写入去重历史。

等待集合使用一个最早截止任务驱动清理，执行后重新计算下一次截止时间；主线程恢复时清理所有已经到期的等待项，不只处理队头。它沿用现有 Scheduler/Handler，不增加线程或协程。请求开始展示后取消其等待过期约束，正常展示时长仍由原策略决定。

不尝试强制中断调用方正在执行的 DSL。准备阶段跨越有效期或页面结束时，退出准备后必须取消且不能显示；额度不得提前重复分配给仍在准备中的请求。

### 3.4 去重历史容量

保留 `(scopeId, groupKey, message)` 结构化键和现有窗口判定。开启容量后使用有上限的访问顺序映射，超限时淘汰最久未访问的历史条目；作用域取消/关闭仍清除对应记录。

不按历史请求的窗口统一清扫全部键，因为后来的请求可能使用不同 `windowMillis`，这样做会改变现有判断。容量淘汰本身意味着一个键被移除后，即使原时间窗口未结束，相同消息也可能重新接受；这是开启有界历史后的明确取舍。

条目上限只约束条目数量，不是消息字符串和业务对象的字节上限。不缓存自定义 View、内容工厂或完整请求到去重历史中。

## 4. 拒绝与过期的状态表达

建议新增 `ToastDropReason` 类型，至少包含 `CAPACITY_EXCEEDED` 与 `EXPIRED`；在 `ToastHandle` 新增只读、可跨线程观察的 `dropReason` 属性，普通请求为 `null`。

为保持旧枚举兼容，两类请求仍以 `State.CANCELED`、`DismissReason.CANCELED` 结束：

| 情况 | `dismissReason` | `dropReason` |
| --- | --- | --- |
| 用户取消、页面停止、旧渲染失败 | `CANCELED` | `null` |
| 容量不足 | `CANCELED` | `CAPACITY_EXCEEDED` |
| 等待过期 | `CANCELED` | `EXPIRED` |
| 正常完成或替换等既有结果 | 原有值 | `null` |

主线程先完成状态转换、设置附加原因、释放额度和移除任务，再发送业务回调。`onCancel` 和 `onDismiss` 各最多一次，不调用 `onShow`；回调抛错不影响其他请求。取消与淘汰竞争时，通过同一主线程转换决定唯一终态，终态原因之后不可覆盖。

现有诊断事件和 detail 格式保持不变，调用方可在终态回调中读取 `handle.dropReason`。容量与过期是正常治理结果，不伪装成渲染 ERROR，也不输出消息正文。

## 5. LifecycleOwner 扩展

### 5.1 模块和接口

新增 `library-lifecycle` 模块，建议发布坐标为 `io.github.logan0817:ktoast-lifecycle:1.2.0`，与核心同版。核心的 POM 和依赖图中不得出现该模块、Lifecycle、Fragment 或 Compose。

扩展提供 `KToastLifecycleScope.create(activity, owner, options)`，返回包装作用域，最少提供核心已有的 `show`、`showDelayed`、`cancel`、`close` 和 Java 配置入口。它不暴露可绕过门禁的原始 `KToastScope`。

采用通用 `LifecycleOwner` 入口，不为调用 Fragment 的 `viewLifecycleOwner` 增加 Fragment 生产依赖。实施采用 `androidx.lifecycle:lifecycle-common:2.5.1`。已核对 2.6.2 的真实 POM 会传递引入协程；2.5.1 提供所需观察 API，仅传递 annotation，不引入 runtime-ktx 或协程。公开签名涉及的核心类型和 LifecycleOwner 通过 `api` 依赖正确暴露。

冻结前检查实际所需 API、minSdk、minCompileSdk、metadata 和传递依赖。扩展单独声明其实际消费者工具链要求，不沿用核心旧 AGP/compileSdk 31 消费者的结论。

拟用法如下，属于新增接口示例：

```kotlin
// 在 Fragment.onViewCreated 中创建并保存。
toastScope = KToastLifecycleScope.create(
    requireActivity(),
    viewLifecycleOwner
)

// 页面已启动后的点击事件中调用。
toastScope.show("保存成功")
```

### 5.2 生命周期语义

使用 `STARTED` 作为默认显示门槛，与核心 Activity 行为保持一致：

| Owner 状态或事件 | 行为 |
| --- | --- |
| Owner 尚未 STARTED | 显示/延时调用以取消结束，包装作用域继续观察 Owner |
| 到达 STARTED | 为该轮活动期创建新的核心 Activity 作用域 |
| 离开 STARTED | 关闭该轮核心作用域，清理当前、队列、防抖、待提交和延时请求 |
| 再次 STARTED | 使用新核心作用域，只接受新请求，不恢复旧请求 |
| DESTROYED 或显式 close | 永久关闭包装作用域并注销观察器 |

优先通过“每轮 STARTED 使用一个核心作用域，停止时 close”实现，复用核心的不可复活语义，不在核心引入 `LifecycleOwner` 或新的通用生命周期框架。

创建必须在主线程执行；显示、取消和关闭延续核心工作线程调用能力。代理切换须安全发布到工作线程；工作线程拿到旧代理后，即使 Owner 已恢复，也不能把旧请求显示在新活动期。停止期间提交的请求不能延后到恢复后显示。

`cancel()` 只清理当前活动期，不关闭包装作用域；取消回调中新提交的请求仍遵守 Owner 门槛。`close()` 立即标记永久关闭，随后在主线程清理；所有关闭流程可重复调用，终态回调重入不能重新激活作用域。

创建时 Owner 已销毁或宿主 Activity 已结束，明确拒绝创建。宿主重建后须创建新包装作用域，不自动换到新的 Activity。宿主弱引用失效、Owner 与宿主先后结束时，均应完成清理。

### 5.3 必须说明的页面边界

Fragment 必须绑定 `viewLifecycleOwner`，不能笼统地绑定 Activity 或 Fragment 自身的生命周期。Fragment 的 hide/show 或自定义路由如果不导致 Owner 离开 STARTED，库不会自动推断“页面不可见”；业务应显式取消，或提供与页面可用状态一致的 Owner。

该扩展仍共享核心的全库串行展示队列，不提供多窗口并行展示。Compose 暂可由业务在受控副作用中接入并清理，核心不会新增 Composable、remember API 或 Compose 依赖。

## 6. 实现落点与内部职责

| 文件或区域 | 必要修改 |
| --- | --- |
| `KToast.kt` | 新运行策略入口；冻结与准入；待提交/延时额度转移和清理；保留旧入口签名 |
| `runtime/ToastRequest.kt` | 内部准入记录、展示资格时间和截止信息；内部模型可调整 |
| `runtime/ToastDispatcher.kt` | 统一终态释放、过期调度、有界去重历史及开始展示前复核 |
| `runtime/ToastHandle.kt` | 新只读附加原因，保持旧状态和方法语义 |
| 新运行策略及附加原因类型 | 参数校验、不可变策略快照和明确的公开文档 |
| 新 `library-lifecycle` | LifecycleOwner 包装、主线程观察和代理切换 |
| `app` | 生命周期切换、容量拒绝、过期及原因展示示例 |
| 发布/校验脚本与 CI | 新模块产物、1.1.0 基线、候选版本参数和消费者验证 |

只有容量额度确实需要跨调用线程和主线程协调时，才提取一个内部准入组件；窗口策略不参与容量计数。配置锁内不执行业务 DSL、窗口调用或回调，防止死锁和长时间占锁。

`cancel`、`cancelGroup`、作用域关闭、替换、防抖覆盖、渲染失败、超时和正常展示，都需审查额度及任务所有权。旧延时 `Runnable` 重复执行、取消后执行、触发与取消竞争时不能重复释放或复活请求。

## 7. API 与发布兼容方案

实施前校验主要使用 1.0.5 基线，按公开成员完全相等比较。本版已增加正式 1.1.0 基线与精确增量；新增 `KToast` 方法或 `ToastHandle` getter 通过审阅清单验收，不关闭兼容检查。

实施顺序：

1. 从正式 1.1.0 AAR 提取完整公开 API，新增 `docs/api/ktoast-1.1.0.json`，保留原始制品摘要与来源；不覆盖 1.0.5 基线。
2. 在 `check_public_api.py` 中集中实现比较逻辑，`verify_candidate.py` 复用。所有旧类、声明、方法描述符必须仍存在；既有枚举和 data class 构造/生成方法继续严格检查。
3. 对本版在旧类上的新增成员维护可审阅的精确增量清单；未列明的新增、删除或改变均报错。新公开类型同时纳入候选 API 报告，不只扫描旧类集合。
4. 保留已编译的 1.0.5 消费者，并增加已编译的 1.1.0 消费者，替换为候选 AAR 验证链接和运行。源码消费者另测 Java 重载歧义和 Kotlin 调用兼容。
5. 新生命周期模块使用独立消费者验证依赖、编译、R8 和运行。核心消费者单独验证，证明未引入扩展依赖。

新增模块需各自具有正确的 artifactId、POM、sources、真实 API 文档和本地候选产物。现有发布脚本与工具包含核心模块路径、单一坐标及产物数量假设，必须逐处检查，不能把核心的签名包或文件数量直接套到双模块发布。

仅为两个实际模块增加必要参数和聚合检查，不顺带改造成通用发布平台。同步检查工作流、兼容消费者、校验工具中的 `1.1.0-SNAPSHOT` 引用；候选版本优先由已有 Gradle 属性传递。旧消费者的冻结版本和 API 基线不随候选版本替换。

## 8. 验证与验收标准

### 8.1 可控时钟的核心测试

复用当前 Runtime/Scheduler 替身，使用虚拟时间验证，避免依赖真实 sleep。

| 风险 | 必须覆盖的行为 |
| --- | --- |
| 默认兼容 | 无策略时保留四种模式、旧取消和旧延时行为；已有测试继续通过 |
| 配置竞态 | 主线程配置与工作线程首个登记竞争时只确定一份快照；冻结后拒绝变更 |
| 容量 | 上限边界、所有待处理阶段、活跃请求不计入、拒绝 REPLACE 不影响当前提示 |
| 额度所有权 | 替换、取消组、全局取消、防抖覆盖、DSL 抛错和渲染失败不泄漏/重复释放 |
| 时间 | 截止边界、主动延时与防抖不被提前算作等待、迟到触发不重置有效期、时间溢出 |
| 清理 | 过期队列尾部也能清除；关闭与恢复不复活旧任务；清空后过期定时器注销 |
| 去重 | LRU 淘汰、不同窗口、分隔符键、作用域清理；未启用时保持旧判断 |
| 回调 | 拒绝和过期各一个终态、主线程回调、原因先于回调可见、异常与重入不阻断推进 |

补一个有界突发自检：在明确的策略下连续提交数千条混合请求，核对有效待处理数不超上限、历史数不超上限，清理后额度归零、无剩余等待任务、所有返回句柄终态唯一。它验证状态和容量，不充当性能跑分或进程内存证明。

### 8.2 生命周期设备测试

Demo 增加最小的双 Fragment 页面，实际验证 A 页延时后切到 B 页、返回 A、销毁并重建 A 的 View。断言旧消息不出现，新活动期请求可显示，关闭和回调只执行一次。

另覆盖 Owner 初始未启动/已启动/已销毁、工作线程准备期间停止再恢复、宿主先于 Owner 结束、显式 close 与 ON_START 交错，以及回调中再次提交。检查观察器、延时任务和宿主引用清理。

继续复用 API 21、30、31、35、36 关键模拟器矩阵和 R8 消费者检查；单独记录扩展实际支持的工具链与设备结果。与窗口相关的既有 IME/RTL 回归继续执行，不把容量测试替代窗口测试。

厂商真机、分屏、无障碍和显示缺口按实际条件补充；缺少设备或 fixture 的项目明确标为未验证/跳过。已有历史成功不能替代本版最终产物的运行证据。

### 8.3 构建和发布产物

实现后先扩展既有 `verifyReleaseCandidate`，聚合核心与新模块必要的测试、Lint、产物和 API 检查，再统一运行。核心本地候选入口仍可沿用：

```bash
bash ./gradlew verifyReleaseCandidate -PVERSION=1.2.0-SNAPSHOT --console=plain
```

旧消费者构建明确传入候选版本，避免回退到脚本旧默认值：

```bash
bash ./tools/compatibility/android-consumer/gradlew \
  -p tools/compatibility/android-consumer \
  assembleDebug assembleRelease \
  -PktoastVersion=1.2.0-SNAPSHOT --console=plain
```

以上入口已用于本地验收；根候选任务同时检查两个模块，扩展消费者位于 tools/compatibility/lifecycle-consumer。当前命令见[发布指南](../RELEASING.md)，产物与设备范围见[1.2.0 验收记录](../releases/1.2.0.md)。

检查两个模块实际解析的 AAR、POM/Gradle metadata、sources 和文档，按摘要关联设备 APK 与候选源码。报告未裁剪 AAR 及同条件消费者 R8 后增量；没有可比测量时不宣传“更轻”或“更快”。

## 11. 采用与回退

旧使用方升级核心后，可先不设置运行策略，保留原行为；需要容量治理的应用在初始化阶段显式开启。Fragment 业务按页面逐步引入扩展，无需全项目替换。

容量或时效策略不适合业务时，在下一次进程启动前移除或调整配置；不提供运行期间热切换。生命周期扩展可由应用停止依赖并恢复原 Activity/显式清理方案，需重新构建应用。

发现发布回归时，应用可将核心及扩展成套回退到可用组合；1.1.0 没有本版扩展，不能仅把核心降到 1.1.0 而保留依赖 1.2.0 的扩展。已发布制品不覆盖重发，修复使用新版本。
